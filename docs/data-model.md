# Supabase data model

Proposed schema for a new, dedicated Supabase project. This is a specification, not a migration. All times use `timestamptz`; all ownership references use `auth.users.id`.

## Meetings

`meetings` contains one row per recording:

| Field | Purpose |
| --- | --- |
| `id`, `user_id` | UUID primary key and owner |
| `client_request_id` | Unique per owner, makes creation idempotent |
| `title` | Default date-based title; optional rename |
| `status` | `draft`, `queued`, `preparing`, `transcribing`, `summarizing`, `ready`, `failed`, `deleting` |
| `audio_path`, `audio_mime_type`, `audio_bytes` | Original recording location and verified metadata |
| `duration_seconds`, `interrupted` | Actual duration and whether capture ended unexpectedly |
| `transcript_markdown` | Nullable Postgres `text`, full assembled transcript |
| `summary_markdown` | Nullable Postgres `text`, generated summary |
| `transcription_model`, `summary_model`, `prompt_version` | Reproducibility metadata |
| `failure_stage`, `error_code`, `error_message` | Safe user-facing failure details |
| `created_at`, `updated_at`, `completed_at`, `deleted_at` | Lifecycle timestamps |

Use `text` fields as the canonical documents. Do not duplicate Markdown into Storage or a separate document service. Copy/download can produce `.md` files from these fields. A summary failure leaves `transcript_markdown` intact. Only trusted server code changes processing fields.

Index `(user_id, created_at DESC, id DESC)` for history pagination. Add uniqueness on `(user_id, client_request_id)` and checks for allowed states and nonnegative durations/sizes.

## Segments and jobs

`meeting_segments`: `id`, `meeting_id`, `segment_index`, `audio_path`, `start_seconds`, `end_seconds`, `status`, `transcript_text`, optional provider timing metadata, model/provider IDs, usage/cost when returned. Unique `(meeting_id, segment_index)`. The final transcript is assembled from successful segments, never from summaries. Keep ordering and overlap metadata to avoid losing words at boundaries.

`processing_jobs`: `id`, `meeting_id`, `stage`, optional `segment_index`, unique `dedupe_key`, `status`, `attempts`, `available_at`, `lease_token`, `lease_expires_at`, safe `last_error`, `created_at`, `finished_at`. Stages are prepare, transcribe, summarize, and delete. Jobs are server-only. An indexed ready-job scan and atomic lease RPC avoid double processing.

A unique summarize job is inserted only when every expected segment is complete. The preparation manifest fixes the expected segment count before transcription begins. Retry keeps successful segments and recreates only missing work. All writes check that the meeting is not tombstoned.

## Live summary snapshots

`meeting_summary_streams`: one row per meeting with `meeting_id` as primary key, `generation_id`, increasing `revision`, `draft_markdown`, `status` (`streaming`, `complete`, `failed`), and `updated_at`. This small table avoids replicating the full transcript on every summary update. Enable its Realtime publication. Owner-only SELECT derives from the parent meeting; writes are worker-only and fenced by the current job lease. Never expose it without RLS.

A new attempt replaces the generation ID and resets its draft. The finalized canonical document remains `meetings.summary_markdown`; partial text is not a completed document. Commit the final summary, completed stream status, and job success together. Clear redundant draft text after completion; the client refetches the canonical document. Delete snapshot rows with the meeting and clear drafts/caches on access loss. See [Streaming UI](streaming-ui.md) for ordering and reconnect rules.

## Private audio storage

One private bucket, `meeting-audio`, with original objects at `{user_id}/{meeting_id}/original.{ext}` and derived files under `{user_id}/{meeting_id}/segments/`. File paths are generated by the server. Original objects are immutable once finalized. Never create public bucket URLs.

The upload policy checks both the first path component and ownership of a draft meeting. Restrict file size/types at the bucket and API, then verify actual contents during preparation. Users can read only their own non-deleting meeting files. Derived object writes and finalized-file mutation are server-only. Sign playback URLs for five minutes and refresh on demand; possession of a live signed URL grants access until expiration.

## Ownership and access

Enable RLS on every exposed table and on Storage. Meeting reads require `auth.uid() = user_id` and `deleted_at IS NULL`. Segment access inherits meeting ownership. Revoke browser writes to server-owned status/output fields; expose only narrow authenticated operations. Keep processing jobs in a private schema or revoke all client grants.

Use session-scoped Supabase clients for normal user access. A server-only service-role client is limited to worker/system operations and must enforce meeting lifecycle itself because it bypasses RLS. Secret-bearing DB functions have fixed search paths and explicit execution grants.

## Retention, deletion, and cleanup

Proposed retention: original audio, transcript, and summary remain until deletion. Remove derived segment audio after successful assembly and summarization; retain enough text metadata for diagnosis/retry without storing duplicate audio forever.

Deletion first hides the meeting and prevents new jobs. Cleanup removes all original/derived Storage objects and then its DB rows. A final reconciliation pass catches objects uploaded by an in-flight worker after deletion began. Retry cleanup failures. Existing signed URLs may remain usable until expiration; provider logs and DB backups follow their own configured retention and are not promised to disappear instantly.

A scheduled cleanup marks abandoned drafts and handles orphan uploads using a documented grace period, proposed at 24 hours. Before public release, implement the same cleanup process for account deletion; do not rely on DB cascade alone to delete Storage objects. Do not log audio, transcript, or summary contents in operational logs.
